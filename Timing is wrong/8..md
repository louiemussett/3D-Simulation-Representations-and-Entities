Not much, provided you change the **calendar abstraction cleanly** instead of replacing every number that looks like `30`, `120`, or a lifespan.

From the code I checked, I would classify this as a **small code change with moderate testing consequences**. The core implementation is probably only a handful of source edits plus updated tests.

The dangerous approach would be:

> change `120` to `365` everywhere.

Do **not** do that.

Some `30`s represent an ecological month, some are unrelated behaviour thresholds, some are scores, distances, cooldowns, damage values, etc. You only want to change calendar assumptions.

## The two places that definitely need changing

Your central clock currently contains:

```js
export const DAYS_PER_ECOLOGICAL_MONTH = 30;
export const DAYS_PER_ECOLOGICAL_YEAR = 120;
```

and observation pacing is calculated from `DAYS_PER_ECOLOGICAL_YEAR`.

Changing:

```js
export const DAYS_PER_ECOLOGICAL_YEAR = 365;
```

would automatically make the observation system scale a 365-day year into the same selected viewing duration.

That is good.

For example, standard observation mode is currently 180 real minutes per ecological year. The formula derives the ecological time represented by each interaction tick from the year length.

So with a 365-day year, you **do not need to make the game take 3× longer** unless you want to.

You could still have:

> **365 ecological days = 180 real minutes**

instead of:

> 120 ecological days = 180 real minutes.

That preserves your intended gameplay pacing.

## But this line absolutely must also change

Your season logic currently contains a literal 120/30 assumption:

```js
const season =
  seasons[
    (
      startingSeason +
      Math.floor(((sim.day - 1) % 120) / 30)
    ) % seasons.length
  ];
```

That means:

- days 1–30 = Spring
    
- 31–60 = Summer
    
- 61–90 = Autumn
    
- 91–120 = Winter
    
- day 121 = Spring again
    

If you changed only the year constant to 365, this code would continue restarting the seasons every 120 days.

So you need to replace this with a calendar-aware seasonal calculation.

## I would not use four equal 91.25-day seasons

You have two sensible options.

For a simple Earth-like calendar, use fixed seasonal boundaries such as:

- Spring: days **1–92**
    
- Summer: **93–184**
    
- Autumn: **185–275**
    
- Winter: **276–365**
    

That gives:

- Spring = 92 days
    
- Summer = 92 days
    
- Autumn = 91 days
    
- Winter = 90 days
    

Or use approximately equal quarters:

- 91
    
- 91
    
- 91
    
- 92
    

The exact split matters much less than removing the hard-coded 30-day assumption.

I would probably centralize it rather than embed another formula in `app.js`.

Something like:

```js
export const DAYS_PER_ECOLOGICAL_YEAR = 365;

export const SEASON_START_DAYS = Object.freeze({
  Spring: 1,
  Summer: 93,
  Autumn: 185,
  Winter: 276,
});
```

and then provide a function such as:

```js
export function seasonForDay(dayOfYear, startSeason = "Spring") {
  // resolve season here
}
```

Then `app.js` only asks the clock/calendar module:

```js
sim.season = seasonForDay(clock.dayOfYear, worldSetup.startSeason);
```

That is much safer long-term.

# The 30-day ecological month does NOT necessarily need changing

This is an important distinction.

Your code also defines:

```js
DAYS_PER_ECOLOGICAL_MONTH = 30;
```

You can keep that if “month” is merely a convenient ecological interval.

A 365-day year could then contain:

- twelve 30-day ecological months = 360 days
    
- plus 5 residual days
    

But that is slightly awkward if the UI actually presents months as calendar months.

From what I examined, the month constant is being used principally as a **time interval**, not as the basis of the displayed year/month date.

For example, woody succession currently does this:

```js
const ecologicalMonth =
  (sim.day + cell.id) % 30 === 0;
```

and the comment explains that woody succession is evaluated roughly once per ecological month per hex.

That code **should probably stay at 30**.

It means:

> check slow vegetation succession approximately every 30 days.

It does not mean:

> the year must contain four months.

So this is exactly why a global search-and-replace would be dangerous.

# The animal ages probably should NOT be changed

This is another important point.

Your animals have biological values such as:

```text
matureAge: 80
gestation: 60
maxAge: 420
```

Those are expressed in **days**.

If you change the year from 120 days to 365 days, those numbers should generally stay the same if they were intended to describe biological durations.

For example, a Valley Grazer with:

- maturity = 80 days
    
- gestation = 60 days
    
- max age = 420 days
    

would change conceptually from:

> maturity at 0.67 years  
> maximum age 3.5 years

to:

> maturity at 0.22 years  
> maximum age 1.15 years.

That exposes a separate question:

**Were those biological ages originally designed assuming a 120-day year?**

If yes, then changing the calendar reveals that many species life-history numbers may need rebalancing.

But technically, you should **not automatically multiply them by 365/120** just to make the calendar work.

Calendar correctness and biological realism are two separate changes.

I would do them separately.

# Observation mode actually makes the transition easier

Your architecture has a useful design feature.

The simulation doesn't say:

> one real second always equals X ecological days.

Instead, it calculates ecological time per interaction tick from:

```js
DAYS_PER_ECOLOGICAL_YEAR
```

and the selected observation duration.

Currently:

```js
OBSERVATION_YEAR_MINUTES = {
  fast: 60,
  standard: 180,
  detailed: 360
};
```

So the current design means:

- fast: one ecological year in 1 real hour
    
- standard: one ecological year in 3 real hours
    
- detailed: one ecological year in 6 real hours
    

Changing the ecological year from 120 to 365 days **doesn't have to alter those wall-clock durations**.

That's excellent.

It simply means each interaction tick represents more ecological time.

Under the current 120-day standard year, the test confirms:

```text
16 ecological minutes per interaction tick
```

at the 180-minute observation setting.

With 365 days instead, that becomes approximately:

[  
365\times1440/(180\times60)  
]

≈ **48.67 ecological minutes per interaction tick**.

So at one interaction tick per real second:

> **1 real second ≈ 48 minutes 40 seconds of ecological time**

and the full 365-day year still takes three real hours.

This is probably exactly what you want.

# Your tests will definitely need changing

The simulation-clock tests currently encode the 120-day year explicitly.

For example:

```js
assert.deepEqual(
  TIME_SKIP_MINUTES,
  {
    minute: 1,
    hour: 60,
    day: 1440,
    month: 43200,
    year: 172800
  }
);
```

`172800` is:

[  
120\times1440  
]

For 365 days it becomes:

[  
365\times1440=525600  
]

So that expected value needs changing to:

```js
year: 525600
```

The test also currently expects one year later to be:

```js
{
  year: 2,
  dayOfYear: 1,
  day: 121,
  hour: 0,
  minute: 0
}
```

With 365-day years that becomes:

```js
{
  year: 2,
  dayOfYear: 1,
  day: 366,
  hour: 0,
  minute: 0
}
```

The observation scaling tests would also change.

Currently they expect:

```js
[60, 180, 360]
```

minutes/year to produce:

```js
[48, 16, 8]
```

ecological minutes per interaction tick.

Those values are based on 120 days.

With 365 days they become approximately:

```text
60-minute year   → 146 ecological min/tick
180-minute year  → 48.667 min/tick
360-minute year  → 24.333 min/tick
```

So the tests need updating accordingly.

# Save games deserve special attention

This is probably the largest compatibility concern.

Your current saves can contain an absolute:

```js
ecologicalMinute
```

value.

If a saved world has already reached, say:

```text
ecological day 240
```

under the old calendar, that meant:

> Year 3, Day 1

because:

[  
240/120=2\text{ completed years}  
]

Under the new 365-day calendar, exactly the same absolute time becomes:

> Year 1, Day 241

The organism ages would still be 240 days old, which is internally sensible.

What changes is the **calendar label**.

So you need to decide what save migration should mean.

### Option A — Preserve absolute biological time

I recommend this.

A world that has experienced 240 ecological days remains 240 days old.

After upgrading, its date changes from:

> Y3 D1

to:

> Y1 D241.

This preserves:

- age;
    
- gestation;
    
- plant age;
    
- ecological history;
    
- injuries;
    
- lifespan;
    
- memories.
    

It only changes calendar interpretation.

This is the safest biological solution.

### Option B — Preserve old displayed year number

You could scale every saved `ecologicalMinute` by:

[  
365/120\approx3.0417  
]

but then an animal that had physically lived 240 days suddenly becomes associated with 730 days of ecological history.

That risks affecting:

- age;
    
- pregnancy;
    
- plant growth;
    
- carcass decay;
    
- memories;
    
- seasonality;
    
- ecological histories.
    

I would **not** do this.

Preserve absolute days.

# Season migration is the tricky save-game part

Imagine an old save on:

> absolute day 100

Under the old 120-day calendar, that's Winter.

Under a new Earth-like year, day 100 would probably be Summer if Spring starts on day 1 with your shifted four-season scheme—or whatever your exact season mapping dictates.

So loaded worlds could change season instantly after upgrade.

That is not necessarily wrong: the old calendar itself was artificial.

But you may want the save schema to note the calendar version:

```js
calendarSchema: 2
```

and migrate deliberately.

Your world already has schema migration infrastructure, so this is the sort of change worth versioning rather than silently altering interpretation.

# Most seasonal ecology probably does not need editing

I checked the uses of `sim.season`.

Most of the downstream systems simply ask things like:

```js
sim.season === "Winter"
```

or:

```js
sim.season === "Summer"
```

For example:

- seasonal weather temperature adjustment;
    
- winter scarcity;
    
- seasonal migration;
    
- climate overlays;
    
- leafless trees.
    

Those systems don't care whether Winter lasts 30 or 90 days.

Once `sim.season` is calculated correctly, they should naturally continue working.

That is why I think the change is fairly contained.

# What I would change

I would make the change in roughly this structure:

1. In `simulation-clock.js`, change:
    

```js
DAYS_PER_ECOLOGICAL_YEAR = 120
```

to:

```js
DAYS_PER_ECOLOGICAL_YEAR = 365
```

2. **Keep**:
    

```js
DAYS_PER_ECOLOGICAL_MONTH = 30
```

for now, because it is being used as an ecological cadence.

3. Add a centralized season-calendar function to `simulation-clock.js`.
    
4. Remove this from `app.js`:
    

```js
Math.floor(((sim.day - 1) % 120) / 30)
```

and replace it with the centralized season calculation.

5. Update the clock tests for:
    
    - 365-day year;
        
    - `525600` minutes/year;
        
    - day 366 = Year 2 Day 1;
        
    - new observation scaling.
        
6. Add explicit season-boundary tests:
    
    - last day Spring;
        
    - first day Summer;
        
    - last day Summer;
        
    - first day Autumn;
        
    - etc.;
        
    - day 365;
        
    - day 366.
        
7. Add a save-migration test.
    
8. Run the entire test suite.

# One more important correction to my earlier answer

Changing to 365 days while retaining the three-hour standard observation year would mean that **real play time per year stays exactly the same**.

So:

> 1 ecological year = 3 real hours

would remain true.

What changes is how much ecological time passes per interaction tick.

That means you can get the scientifically more intuitive 365-day annual calendar **without making the game three times slower**.

That is probably the cleanest solution.

So I would say: **calendar conversion itself is quite manageable and low-risk if centralized properly. The thing most likely to “screw up everything” would be a global replacement of 30/120 constants or trying to rescale existing ages and saves indiscriminately.**
